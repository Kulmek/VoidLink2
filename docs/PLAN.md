# План развития Tunnel

## Этап 0 — MVP (сделано)

- Рандеву-сервер + релей, клиенты с Wintun-адаптером, ping между пирами.
- UDP hole punching → direct P2P, шифрование ChaCha20-Poly1305.

---

## Этап 1 — Идентичность и группы (протокол v2)

### 1.1 Идентичность клиента
- При первом запуске клиент генерирует **ed25519-ключевую пару**, хранит в
  `%APPDATA%\tunnel\identity.json`. Это постоянная «личность» пользователя.
- **Friend code** — компактная форма pubkey для передачи другу:
  `TUN-XXXX-XXXX-XXXX-XXXX` (base32 + контрольные символы). Добавление друга =
  вставка кода.

### 1.2 Группы
- Группа = отдельная виртуальная сеть, у каждой своя подсеть
  (базовый префикс настраивается на сервере, по умолчанию
  `100.66.<i>.0/24`, CGNAT-диапазон, как у Tailscale).
- Атрибуты: id, имя, владелец (pubkey создателя), публичная/приватная,
  участники (pubkey → IP), kick/ban-список (управляет владелец).
- **Публичная** — видна всем в списке, вход по желанию.
- **Приватная** — видна только участникам; вход по приглашению владельца
  (клик/команда → у друга появляется запрос «вас пригласили в группу X»).

### 1.3 Выдача IP сервером
- Сервер держит lease-таблицу `pubkey → ip` на группу. Участник при возврате
  получает **тот же IP** (стабильность, как в Hamachi).
- Клиент IP никогда не выбирает сам; сервер гарантирует уникальность.
- Освобождение lease по таймауту (10 мин офлайн) либо по явному leave.
- Конфликтов «кто первый» нет — назначает только сервер.

### 1.4 Шифрование v2
- Сервер перестаёт быть «читателем» трафика: в DATA-фрейме dst_ip и group_id
  уходят в открытый заголовок, payload остаётся под AEAD ключом группы.
  Релей читает только заголовок (end-to-end даже от сервера).
- Ключ группы генерирует сервер и раздаёт участникам при join (по каналу,
  зашифрованному их identity-ключами).

---

## Этап 2 — Состояние сервера

- `server.json` рядом с exe: группы, участники, leases. Сохранение при
  изменениях; группы выживают рестарт сервера.
- Онлайн-сессии (SocketAddr → pubkey) отдельно, в памяти.
- Таймауты: участник офлайн → исключается из онлайн-списка, lease держится.

---

## Этап 3 — Ядро клиента (engine)

- `engine` = отдельный модуль без UI: подключение, события, TUN-мост.
- Один адаптер на все группы: несколько IP на один Wintun-адаптер
  (`netsh add address`); пересоздание маршрутов при join/leave группы.
- События для UI: PeerOnline, PeerOffline, DirectUp, GroupJoined, GroupLeft,
  InviteReceived, Error.
- Локальный стор `config.json`: identity, друзья (pubkey + отображаемое имя),
  автоприсоединение к группам при старте.
- UI ↔ engine через каналы (mpsc), UI не лезет в сеть сам.

## Этап 4 — TUI (ratatui)

```
┌ Группы ─────────────┬ Группа "gamers" (публичная) ─────────────┐
│ ● gamers     3/253  │  имя     IP            связь    ping    │
│ ● work       2/253  │  alpha   100.66.0.2    direct    1 мс    │
│ 🔒 secret    2/253  │  bravo   100.66.0.3    relay     45 мс   │
├ Друзья ─────────────┤                                          │
│ ● alpha (2 группы)  │                                          │
│ ○ charlie           │                                          │
└─────────────────────┴──────────────────────────────────────────┘
 100.66.0.2 @ 127.0.0.1:5555   [F2 создать] [a добавить друга] …
```

- **Группы**: создать (F2), удалить (F8, только владелец), переименовать (F6),
  пригласить друга (i), покинуть, список публичных → войти (j).
- **Друзья**: добавить (a, вставка friend code), удалить (d, с
  подтверждением), Enter по другу → карточка: в каких группах он состоит
  (запрос серверу: публичные группы друга + общие с тобой).
- **Popup'ы**: ввод текста, выбор друга для инвайта, подтверждения.
- **Статус-бар**: мой IP, сервер, счётчик direct/relay.
- **Лог**: последние события (подключения, ошибки) отдельным блоком/вкладкой.

### Скоуп TUI (волна 1, утверждён)

| Фича | Суть | Серверная часть |
|---|---|---|
| RTT в списке пиров | клиент шлёт PING/PONG раз в 1 с, живая задержка у каждого пира | нет |
| Тосты | вход/выход участников, приглашения, ошибки — гаснут через 5 с | нет |
| F1 справка | оверлей всех хоткеев | нет |
| Цветовой код | зелёный direct / жёлтый relay / серый offline | нет |
| График трафика | sparkline КБ/с + счётчики пакетов в статус-баре | нет |
| Поиск/фильтр | печать — фильтрация списка, сортировка имя/онлайн/RTT | нет |
| Командная строка | `:join`, `:invite`, `:kick`, `:help` | kick — да |
| Kick/ban | удаление участника владельцем | да |
| Копирование в буфер | IP пира, свой IP, friend code | нет |
| Экран настроек | имя, сервер, автовход в группы, темы | нет |

### Профиль (утверждён)

- Карточка профиля: имя (редактируемое), friend code в буфер (текстовая
  форма — пересылается любым мессенджером; QR убрали как излишний).
- Identicon-аватар из pubkey (постоянный «пиксельный» узор пира).
- Статус-текст, рассылается в ростер.
- Статистика: трафик, время в сети, группы.

Позже: мультипрофили, экспорт/импорт identity-файла, статус invisible.

Зависимости: `ratatui` + `crossterm`.

## Этап 5 — Тесты и полировка

- 3+ клиента, join/leave, рестарт сервера (персистентность), возврат с тем же IP.
- Реальный NAT: два компа за разными NAT, проверка relay-фолбэка.
- Потеря сервера: клиенты продолжают P2P, реконнект к серверу с backoff.

---

## Развёртывание

- **Клиенты — только Windows** (Wintun-драйвер, запуск от администратора).
- **Сервер — Linux**: крейт `tunnel-server` чисто кроссплатформенный (std +
  crypto, без windows-зависимостей). Сборка под Linux: `cargo build --release`
  на хосте или в CI; бинарник + systemd-юнит:

  ```ini
  [Service]
  ExecStart=/opt/tunnel/tunnel-server 0.0.0.0:5555 $ROOM_KEY
  Restart=always
  DynamicUser=yes
  NoNewPrivileges=yes
  ProtectSystem=strict
  StateDirectory=tunnel   # сюда ляжет server.json
  ```
- Правила файрвола на сервере: только UDP-порт (5555) наружу/внутрь.

---

## Принятые решения

1. **Друзья** — хранятся локально у клиента; сервер не знает список дружб.
2. **Публичные группы** — свободный вход (увидел в списке → вошёл).
3. **Адресация** — `100.66.0.0/16` (CGNAT-диапазон), группа `i` →
   `100.66.<i>.0/24`.
4. **Порядок работ** — сначала протокол v2 + сервер + engine, затем TUI.

## Порядок реализации

1. `protocol v2`: identity (ed25519), friend code, фреймы групп, DATA с
   открытым заголовком (group_id, dst_ip) + AEAD payload.
2. Сервер: группы, lease-таблица IP, персистентность `server.json`,
   инвайты, список публичных групп.
3. Client engine: локальный стор (identity, друзья, автозапуск), мульти-IP
   на адаптере, события для UI.
4. TUI ratatui: экраны Группы/Друзья, popup'ы, статус-бар, лог.
